# 三国·无双守关：游戏设计 v0.1

更新日期：2026-10-11。名称为工作名。本文用于讨论与首版开发，全部数值均为待试玩调整的试验参数。

## 1. 已确定的方向

- 三国题材，移动端优先，竖屏、单手操作。
- 核心满足感是武将一招横扫成片敌军；敌潮、技能表现、局内快速成长优先。
- 初期通过 GitHub Pages 提供免费网页试玩，后续在 TapTap 宣传并以小游戏形态发行。
- 发行成本尽量低；目前不能把“TapTap 小游戏免软著”视为已确认条件。

以下为本版推荐设计，后续可以根据试玩改变。

## 2. 一句话玩法与核心体验

玩家选择一名三国主将，在城关前部署军阵，拦截并聚集敌军；积攒怒气后，在恰当时机释放无双技，斩开密集敌潮，再用军粮强化下一轮防线。

核心体验链：布阵 → 敌潮聚集 → 压力上升 → 无双横扫 → 军粮入账 → 攻击形态进化 → 更大敌潮。

三条设计原则：

1. 第一局尽快体验清场：前 20 秒内争取出现第一次可主动释放的无双。
2. 普通军阵创造清场机会：位置、攻击覆盖和减速让敌人形成有价值的目标。
3. 无双清杂兵，军阵处理幸存精锐：技能强大，但胜负仍取决于防线。

“横扫千军”是体验目标。首版以清晰可见的密集敌群表现它，实际同屏数量由真机性能验证决定。

## 3. 战场、视角与操作

### 战场

- 2D 俯视略带斜角，敌军从上方两个入口沿预设路线前进，在下方城关前汇合。
- 6 个固定营位，前段能提早削弱单路，汇合处能集中输出，下段便于处理突破者。
- 主将驻守城关附近，自动进行基础攻击；本版不操作主将走位。
- 先做一张架空三国关隘地图，避免第一版承担完整历史战役叙事。

### 竖屏界面

- 顶部：波次、城关耐久、暂停。使用很小的界面高度，优先留给战场。
- 中部：路线、敌军与营位。只给精锐、首领和受损城关常驻血条。
- 底部：军粮、主将头像和怒气、建造/升级面板。无双按钮保持在拇指易触及区域。
- 升级与强化选择时暂停战斗；长屏增加战场可见空间，不放大操作距离。

### 输入

1. 点击营位，底部显示建造或升级选项。
2. 点击选项完成操作；取消不扣资源。
3. 怒气满时点击主将头像，一次点击释放无双。
4. 自动选择有效范围内最密集的敌群；按钮就绪时在战场预显示拟攻击区域，施放时锁定目标。

首版保留施放时机的判断，避免把高频精确瞄准加入单手操作。目标选择应确定、可预期，不能在按下后临时换到另一路。

## 4. 主将与无双

每局只选 1 名主将。最早可玩版本仅做关羽，随后加入周瑜用于对照测试。这样角色辨识度集中，也避免多名武将共用怒气时总是释放最强技能。

| 主将 | 自动攻击 | 无双技 | 适合场景 | 后续可见强化 |
| --- | --- | --- | --- | --- |
| 关羽 | 近关隘的短刀波 | 从主将向选定方向展开宽阔贯穿刀波 | 两路汇合处已经堆积的敌群 | 刀波加宽、追加斩、击退精锐 |
| 周瑜 | 火矢 | 在目标区域形成持续约 4 秒的火场 | 敌人持续进入同一区域 | 延长火场、火焰传燃、形成火墙 |

关羽优先保证普通步兵在覆盖区域内被一击击败；范围外敌人照常推进。重甲兵、敌将承受部分伤害，不被无条件秒杀。周瑜产生持续伤害，通过后续进入的敌人兑现总伤害，而非简单替换关羽的瞬间效果。

两名主将不以谁的总伤害数值更大作为唯一差别，测试应分别提供“瞬间密集敌潮”和“持续长队”两种场景。

### 无双的反馈

- 按下后立即产生主将动作与技能音效，尽快看见第一批敌人受击。
- 试验表现：约 80–120 毫秒命中停顿，短促刀光/火势，适量震动或镜头反馈。
- 集中显示一次击破数量，例如“击破 42”，避免每个小兵都弹伤害数字。
- 普通敌人以击退、消散、旗帜散落等表现退场；核心是清场的力量与秩序变化。
- 特效结束后立即看得清幸存精锐、城关和下一路来敌。允许关闭震动与减弱屏幕晃动。

## 5. 怒气与成长资源

### 怒气

| 参数 | 首轮试验值 |
| --- | --- |
| 上限 / 无双消耗 | 100 / 100 |
| 开局怒气 | 40 |
| 普通军阵处于有效交战时 | 每秒 +4，整个玩家阵营总计一次 |
| 没有交战时 | 每秒 +1 |
| 无双施放后的恢复期 | 6 秒，暂停产怒 |
| 无双及其持续伤害 | 不额外产怒 |

交战按时间累计，不随攻击次数、命中人数、军阵数量增加。连续交战时，开局理论约 15 秒就绪，之后理论约 31 秒一次；实际还取决于敌波间隙。暂停菜单和升级选择期间不推进交战时钟，也不产怒。

群体击杀给军粮，不能立即把下一次无双充满。首版不提供提高怒气效率的强化，以便先验证清场节奏。

### 军粮

军粮用于建造与升级军阵，是局内唯一消费货币。试验值：开局 120、基础建造 60、首次升级 60、二次升级 100；普通兵奖励 1、精锐奖励 3。升级数值与敌波规模联动调整，不把这些值当作最终平衡。

每个敌人死亡仅结算一次军粮。大招清场的收益可以让玩家更快建设防线，但不能在同一帧重复领取击杀奖励。

### 战术强化

指定波次结束后进行三选一，暂停战斗。首版安排约 4 次，优先改变攻击形态；候选项依据已建军阵筛选，避免给玩家无法使用的选项。

- 弓营：箭矢贯穿、追加齐射、优先攻击突破者。
- 投石营：爆炸扩大、命中后短暂减速、针对重甲提高伤害。
- 盾营：增强减速、扩大控制范围、提高对骑兵的阻滞效果。

最早版本先验证军阵建造和升级，再加入三选一。不能同时引入装备、兵种合成和独立武将等级三套局内成长。

## 6. 军阵与敌军

### 3 类军阵

| 军阵 | 功能 | 布阵取舍 |
| --- | --- | --- |
| 盾营 | 有限减速与近距离攻击，帮助形成敌群 | 提前聚敌便于无双；靠后部署更便于救险 |
| 弓营 | 持续、稳定的远程输出 | 提早部署能多攻击几轮；汇合处能覆盖两路 |
| 投石营 | 低频范围伤害，对聚集敌群有效 | 配合盾营收益更高；单独面对分散骑兵效率较低 |

盾营不无限冻结敌军：减速有范围、上限和对重甲的折减，敌人仍会逐步突破。首版采用固定路线与范围判定，避免大量士兵之间的复杂物理碰撞与寻路。

### 3 类敌兵与 1 名首领

- 普通步兵：数量最多，提供清场、军粮与敌潮视觉。
- 疾行骑兵：移动快，迫使玩家关注两路压力和提前拦截。
- 重甲兵：数量少、形体明显，能在无双后存活；考验后续输出。
- 攻城首领：最后一轮出现，分段召唤随从；军阵持续处理首领，无双处理护卫兵群。

两路应有不同的出兵节奏。后期不只增加血量，还通过敌群密度、出兵间隔、精锐混编改变施放时机。

## 7. 一局约 4 分钟的节奏

时间以战斗时钟计算，升级与菜单暂停不计入。以下为关卡编排目标，不是强制倒计时胜利。

| 时间 | 内容 | 玩家应感到的变化 |
| --- | --- | --- |
| 0–30 秒 | 简短的实战建造引导，初始军阵，第一次无双 | 明白“守关、攒怒、一招清场” |
| 30–90 秒 | 敌群变密、第一次关键升级 | 弓箭/刀波等攻击表现明显变化 |
| 90–150 秒 | 两路压力错开，加入骑兵 | 需要判断补哪一路、何时施放 |
| 150–210 秒 | 重甲混入敌潮，出现第二次成长高潮 | 清场后仍有值得处理的精锐 |
| 210–240 秒左右 | 攻城首领与最后几组护卫 | 最后一轮防守与爆发 |

胜利：末波首领及其护卫全部击败，且城关耐久大于 0。失败：城关耐久耗尽。首领存活时继续战斗，避免到 4 分钟自动判胜。

结算展示主将、胜败、最大单次击破数量和关键强化，并提供直接重试。第一版不依赖大量局外战力才能通关。

## 8. 美术与音效建议

推荐试验风格：2D 国风剪影配合简化小兵，突出关羽的长刀轮廓、周瑜的火攻色彩。英雄与精锐明显大于普通小兵，降低密集战场的识别成本。

首版优先制作一个有记忆点的关羽无双、两类命中效果和清晰的军阵攻击；大量立绘、长技能演出、完整配音放到核心玩法验证之后。素材来源与使用许可在项目中留记录。

## 9. 初期试玩与后续发行路径

### GitHub Pages：免费网页试点

GitHub Pages 是 HTML、CSS、JavaScript 静态站点托管服务，适合承载本项目初期的纯客户端试玩。[GitHub Pages 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

推荐产物为可独立部署的 H5 构建目录：入口页面、脚本、本地资源。不依赖账号、支付或游戏服务器；仅保存音量、最高纪录和解锁主将等少量本地进度。浏览器试玩存档不默认承诺与后续 TapTap 存档互通。

部署时必须验证项目子路径下的资源加载、首次点按后开启音频、切到后台暂停、手机浏览器高度变化，以及 HTTPS 访问。试玩反馈最初可通过仓库 Issues 或手动反馈收集；Pages 本身不承担在线排行榜或玩家数据接口。

Pages 官方限制包括发布站点不超过 1 GB、每月 100 GB 的带宽软限制，并限制用它免费托管在线业务、交易网站或商业 SaaS。因此本阶段定义为免费项目试玩；收费与广告运营的部署另行规划。[GitHub Pages 使用限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)

### TapTap：优先核实 H5 小游戏路线

官方介绍区分普通小游戏与 H5 小游戏。[小游戏介绍](https://developer.taptap.cn/minigameapidoc/quick-start/guide/minigames-intro/)

与 GitHub Pages 更接近的是 H5 路线。官方接入说明写明 H5 以网页形式打包，部署在平台域名下；MCP 文档也提供上传本地构建目录的示例。因此推荐迁移 H5 构建产物，再按 H5 专门文档接入所需平台能力，不将 GitHub Pages 地址视为直接上线凭据。[官方接入说明](https://developer.taptap.cn/agents/)、[H5 接入文档](https://developer.taptap.cn/minigameapidoc/quick-start/mcp-guide/mcp-setup/)

普通小游戏使用另一套运行环境，官方说明其缺少浏览器 BOM/DOM；Cocos 适配插件支持 3.8.x 及以上版本。如果后续选择普通小游戏，应重新验证引擎与导出链路，不能把浏览器页面直接视为兼容版本。[普通小游戏引擎适配](https://developer.taptap.cn/minigameapidoc/dev/engine/Cocos-Laya-Egret/)

### 资质与成本的已知边界

- 官方开发者入驻流程包含个人主体认证，但具体发布能力仍取决于产品形态与后台审核。[开发者入驻流程](https://developer.taptap.cn/minigameapidoc/quick-start/guide/registration-login/)
- 小游戏创建文档写明“不涉及内购功能”的小游戏无需提交版号，并要求普通小游戏在正式上架前完成前置备案。这是平台文档条件，不能扩展为所有形态、所有运营方式均免资质。[创建小游戏](https://developer.taptap.cn/minigameapidoc/quick-start/guide/creation-improvement/)
- 同一套小游戏审核规范第 6.5 节仍要求软著登记号和证书，未查到对本项目拟采用的移动端 H5 正式发行明确免软著的条款。预算不以免软著为前提，正式接入时按后台资质分析并确认适用要求。[小游戏审核规范](https://developer.taptap.cn/minigameapidoc/tap-operation/operation-standards/review-standards/)、[资质分析说明](https://developer.taptap.cn/v3/cli/skills/taptap-qualification.md)
- 创建文档允许经资料审核后先发布“敬请期待”或“预约”页面；这与能公开游玩的上线状态不同。后续可先用实际试玩画面宣传，再逐步完成公开游玩的接入与资质。[创建小游戏](https://developer.taptap.cn/minigameapidoc/quick-start/guide/creation-improvement/)

本次仅完成设计与公开资料核查，不代用户注册主体、办理资质或操作对外发布。正式接入前需要核实 H5 路线的软著、备案、登录与商业化要求。

## 10. 技术方向建议

优先方案：2D HTML5 Canvas + TypeScript，构建静态 H5 资源。理由是先满足浏览器试玩，再沿 TapTap 官方 H5 形态接入，减少前期导出与平台改造工作。具体工具与版本在开始写游戏时固定。

战斗逻辑、渲染、平台能力分开：

- 战斗逻辑：波次、敌人、军阵、怒气、军粮、胜负；不依赖 DOM 或平台登录。
- 表现与输入：绘制、触摸、音效、特效、屏幕适配。
- 平台适配：本地存档与后续平台存档、分享、广告等接口。

性能先试验同屏约 100–150 名敌人，逐步增加密度。沿固定路线移动，复用敌人和特效对象，避免每个小兵携带复杂 UI、寻路和持续粒子。选择代表性 Android 手机与 iPhone 浏览器验证，大招释放时争取保持 30 FPS 以上；实际设备型号需在测试前指定。

试验资源目标：首个战斗场景所需资源约 5–10 MB。它是本项目加载目标，不是 TapTap 官方包体上限；不把官方不同文档中的包体限制混为一个确定数字。

## 11. 分阶段范围与验收

| 阶段 | 必须做出的内容 | 进入下一阶段的依据 |
| --- | --- | --- |
| 核心原型 | 关羽、1 张地图、6 营位、盾/弓两类军阵、普通兵/重甲兵、怒气与胜负、重试 | 清场有明显力量感；布阵与施放时机影响结果 |
| Pages 试玩版 | 加入骑兵、投石营、约 4 分钟完整关卡、首领、9 个候选强化、本地设置与纪录 | 手机完整玩通；收集首次使用与重复游玩反馈 |
| 主将对照版 | 加入周瑜与持续敌潮变化 | 两种无双都有人愿意使用，差异能被玩家说清 |
| TapTap H5 测试与发行 | 平台包体自测、实际宣传物料、适用资质与能力接入 | 后台要求满足、真机稳定、试玩问题解决 |

首版暂不加入抽卡、付费战力、装备系统、联盟、联网对战、每日任务、大量武将和完整历史关卡。后续优先增加新的无双方式与出兵组合。

建议先邀请 10–20 位试玩者，作为方向性测试而非统计结论。每人先不看攻略试玩一次，再尝试一局不同布阵。

| 要验证的问题 | 记录方式 | 调整方向 |
| --- | --- | --- |
| 能否快速理解操作 | 是否在 20 秒内主动释放第一次无双；首次犹豫位置 | 引导、按钮位置、初始怒气 |
| 清场是否值得期待 | 最大单次击破、施放前后敌群变化、玩家口述满意度 | 密度、覆盖、命中与声音反馈 |
| 布阵是否有价值 | 相同波次与强化下，两套站位的漏兵和城关耐久 | 路线、射程、减速与覆盖 |
| 有没有主动重试意愿 | 结算后是否立即重开、愿意尝试什么变化 | 波次变化、局内成长、结算入口 |
| 性能是否影响爽感 | 帧率与大招瞬间卡顿、测试设备 | 同屏数量、对象复用、特效预算 |

结算与测试数据先在本地展示或手动记录。外部统计服务的接入需要在设计与部署阶段另行决定。

## 12. 后续最值得讨论的内容

1. 美术走更夸张的国风剪影，还是更亲切的 Q 版武将？
2. 关羽无双更偏向宽阔瞬间横斩，还是沿道路推进的连续刀波？
3. 核心试玩通过后，下一位武将优先做火烧连营、骑兵贯穿，还是震退救场？

第一优先级仍是把关羽的一次清场做得让人愿意再按一次，再扩充武将与发行功能。
